# ПР11 — Формы в Django

Индивидуальный проект «Сервис учёта тренировок», продолжение ПР10.
Материалы Яндекс Практикума не входят в выполненную часть.
Ниже сохранена документация прошлых работ; при различиях актуален этот раздел.

## Запуск после получения проекта

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

Существующую базу не удаляйте. Миграция exercises.0003_exercise_image добавляет
необязательное изображение и сохраняет прежние записи. Перед обновлением своей
рабочей копии сохраните резервную копию db.sqlite3 и media/.
В готовом архиве приложена копия текущей базы с применённой миграцией.
Для новой пустой базы после migrate можно выполнить
`python -m db.import_sqlite_to_orm`. Повторный импорт для уже заполненной базы
не нужен: он может перезаписать изменённые пользователем данные.

Для административной панели используйте свою существующую учётную запись
или создайте её: `python manage.py createsuperuser`.
Пользователь сервиса users.User не является учётной записью входа Django.

## Новые страницы и действия

| Адрес | Назначение | Метод |
|---|---|---|
| `/workouts/` | Форма фильтрации, сортировка, пагинация | GET |
| `/workouts/create/` | Создание тренировки с упражнениями | GET, POST |

redirect на карточку объекта (Post/Redirect/Get), выводится сообщение.

- `workouts/forms.py`: WorkoutFilterForm (forms.Form), WorkoutForm (ModelForm),

- `workouts/views.py`: фильтры из cleaned_data, создание, редактирование через

- `exercises/forms.py`: ExerciseForm и валидатор размера изображения.
- `exercises/models.py`: ImageField с upload_to, необязательное поле image.
- `exercises/views.py`: обработка request.POST и request.FILES, сохранение формы.
- `templates/includes/form_fields.html`: подписи, значения, подсказки,
  ошибки отдельных полей и non_field_errors.
- `workouts/templates/workouts/workout_form.html`: management_form, ошибки
  formset, CSRF и поля родителя/упражнений.
- `homepage/static/homepage/js/workout_form.js`: добавление строк упражнений;
  сервер дополнительно ограничивает число строк и проверяет данные.
- `tests/test_forms_pr11.py`: 39 новых проверок форм и пользовательских сценариев.

## Проверки и правила предметной области

WorkoutFilterForm принимает GET-параметры q, user, type, start, end, sort, active.
DateField преобразует даты; clean() проверяет порядок границ периода.
При неверной дате/периоде показываются ошибки и пустая выборка.
Некорректные необязательные user/type/sort обрабатываются как в ПР10:
ошибочный селектор игнорируется, сортировка заменяется исходной; теперь форма
также показывает причину ошибки. Для фильтрации используются только очищенные
значения полей. Пагинация сохраняет GET-параметры.

Дата выполненной тренировки не может быть в будущем. Подходы, повторения,
вес и длительность неотрицательны. Тренировка должна иметь хотя бы одно
упражнение, в том числе после удаления строк при редактировании. Если форма
или хотя бы одна строка неверна, родитель и строки не сохраняются.
При ошибке сохраняются введённые текстовые значения; файл браузер может
потребовать выбрать повторно.

Статус не включён в пользовательский ModelForm: новая тренировка получает ACTIVE,
редактирование сохраняет прежний статус. Отмена меняет только ACTIVE на CANCELLED,
не удаляет упражнения и повторно безопасна. Завершённые и отменённые записи
не переводятся в другой статус этой кнопкой. Статусы COMPLETED/CANCELLED
отображаются в прежней статистике по правилам ПР10.

В отличие от Roomly, сервис не бронирует ресурс: несколько тренировок пользователя
за один день допустимы. Поэтому искусственный запрет совпадений даты и пользователя
не добавлялся. Пункты методички о занятости помещения адаптируются к проверке
даты, состава тренировки и её статуса. Редактирование той же записи без изменения
даты допускается и не создаёт новую тренировку. Упражнения из справочника выбираются
через ModelChoiceField: несуществующий идентификатор отклоняется.

Все изменяющие данные формы используют POST и csrf_token. GET адреса отмены
возвращает 405, POST без CSRF при включённой проверке — 403. Отсутствующий
объект изменения или отмены обрабатывается через get_object_or_404().
Как и в прежнем учебном интерфейсе, пользовательские формы не требуют входа;
авторизация и разграничение доступа для публичного размещения — отдельный этап.

## Изображения

Pillow добавлен в requirements.txt. Exercise.image хранит путь, сам файл находится
в MEDIA_ROOT (`media/`), URL начинается с MEDIA_URL (`/media/`). На локальном
сервере файлы раздаются только при DEBUG=True. В production их должен раздавать
настроенный веб-сервер или файловое хранилище.

Форма принимает JPEG, PNG и WebP до 5 МБ; ImageField проверяет содержимое файла,
а не только расширение. В HTML указано enctype="multipart/form-data".
Изображение выводится на карточке упражнения только при его наличии.
Редактирование без нового файла сохраняет прежнее фото, флажок очистки убирает
ссылку из записи. Замена и очистка поля не удаляют старые файлы с диска автоматически
(стандартное поведение Django). media/ исключён из Git, храните его резервную копию.
Поле доступно также в административной карточке упражнения.

# Сервис учета тренировок

## Назначение

Приложение для учета тренировок: пользователь записывает тренировки,
отслеживает прогресс, анализирует нагрузку и видит динамику результатов.
Консольная версия приложения (ПР1–ПР3) дополнена веб-интерфейсом на Django
(ПР5), страницы которого с ПР6 строятся на шаблонах Django. С ПР7 данные
веб-интерфейса хранятся в базе данных SQLite, а с ПР9 они описаны моделями
Django и читаются через Django ORM.

Приложение позволяет:

* просматривать упражнения в браузере;
* просматривать информацию об отдельном упражнении и о том, в скольких
  тренировках оно выполнялось;
* искать упражнения по группе мышц и части названия;
* просматривать список тренировок в браузере: искать по имени и типу,
  фильтровать по периоду дат, пользователю, типу и признаку «только
  активные», сортировать и листать по страницам (ПР9);
* просматривать информацию об отдельной тренировке, её пользователе и
  выполненных упражнениях;
* просматривать статистику по активным тренировкам: сводку, популярность
  упражнений, тоннаж по группам мышц, активных пользователей;
* в консольной версии: добавлять упражнения, искать и фильтровать их,
  создавать и отменять тренировки, формировать результат за период,
  смотреть статистику, работать с пользователями;
* хранить данные между запусками приложения в JSON-файлах (консольная
  версия) и в базе данных SQLite, с которой веб-интерфейс работает через
  модели Django.

## Целевая аудитория

Люди, которые стремятся к здоровому образу жизни и хотят увеличить свою
спортивную активность.

## Используемые технологии

* Python 3;
* Django 5.2 — веб-фреймворк;
* Django Template Language (DTL) — шаблоны страниц;
* HTML5 — разметка веб-страниц;
* CSS3 и Bootstrap 5.3 — оформление страниц (Bootstrap подключён через CDN);
* JavaScript — небольшое клиентское поведение (текущий год в подвале);
* SQLite — реляционная база данных; в ПР7 с ней работали через модуль
  `sqlite3` и SQL-запросы, с ПР9 — через Django ORM;
* модели Django, связи (`ForeignKey`, `ManyToManyField`) и миграции (ПР9);
* pytest и pytest-django — автоматизированные тесты;
* flake8 — проверка качества кода;
* black — форматирование кода.

## Предметная область

Основные объекты предметной области:

* упражнение — запись справочника (название, группа мышц);
* пользователь — тот, кто записывает тренировки;
* тренировка — выполненная пользователем тренировка со списком упражнений;
* результат за период времени — тренировки пользователя за выбранный период.

Бизнес-правила:

* тренировку нельзя создать без хотя бы одного упражнения;
* дата тренировки не может быть в будущем;
* подходы и повторения не могут быть меньше нуля;
* тип тренировки — только «кардио» или «силовая»;
* конец периода результата не может быть раньше его начала;
* отмена тренировки не удаляет её: объект остаётся в коллекции, а
  отменённая тренировка не учитывается в статистике и результатах.

## Основные сущности

### Exercise — упражнение

Атрибуты: `id`, `name`, `muscle_group`.
Методы: `is_for_muscle_group()` — проверка группы мышц; `__str__()`.

### User — пользователь

Атрибуты: `id`, `name`, `registered_at`.
Методы: `from_data()` (`@classmethod`) — создание из данных JSON; `__str__()`.

### WorkoutExercise — выполненное упражнение

Атрибуты: `exercise` (объект `Exercise`), `sets`, `reps`, `weight`.
Методы: `is_valid()`, `tonnage()`, `__str__()`.

### Workout, CardioWorkout, StrengthWorkout — тренировки

`Workout` — базовый класс. Атрибуты: `id`, `user` (объект `User`),
`workout_date`, `exercises` (список `WorkoutExercise`), `duration_min`,
`is_cancelled`. Методы: `cancel()`, `is_in_period()`, `is_valid_date()`
(`@staticmethod`), `__str__()`.
Подклассы `CardioWorkout` («кардио») и `StrengthWorkout` («силовая»)
переопределяют `__str__()`: кардио показывает длительность, силовая —
суммарный тоннаж.

### Result — результат за период

Атрибуты: `id`, `user` (объект `User`), `period_start`, `period_end`,
`workouts` (список объектов `Workout`).
Методы: `get_stats()` — статистика по неотменённым тренировкам; `__str__()`.

Объекты хранят ссылки друг на друга (`workout.user`,
`workout.exercises[i].exercise`, `result.workouts[i]`), поэтому и консольная,
и веб-версия работают с одними и теми же объектами.

GET-параметры страниц с данными:

| Страница | Параметры |
|---|---|
| `/exercises/search/` | `muscle_group` (группа мышц), `name` (часть названия) |
| `/workouts/` | `q` (поиск по имени пользователя и типу), `user` (id пользователя), `type` («кардио» или «силовая»), `active=1`, `start` и `end` (даты `ГГГГ-ММ-ДД`), `sort` (`date`, `date_asc`, `user`, `duration`, `tonnage`), `page` |

Некорректные значения не приводят к ошибке: неверная дата показывает
сообщение, неизвестные `type`, `user` и `sort` игнорируются, неверный `page`
заменяется ближайшей существующей страницей, неверный `min_workouts` — значением
по умолчанию.

Если упражнение или тренировка с указанным идентификатором не найдены,
страница возвращает код статуса 404. Для любого адреса, которому не нашлось
маршрута, срабатывает обработчик `handler404` — собственная страница
«404 – страница не найдена» (`homepage.views.page_not_found()`, шаблон
`homepage/404.html`).

Маршрутизация двух уровней: корневой `workout_app/urls.py` подключает
маршруты приложений через `include()`, а конкретные адреса описаны в
`urls.py` каждого приложения.

## Веб-интерфейс и шаблоны Django

Веб-часть приложения реализована на Django. HTML формируется не в Python-коде,
а в шаблонах: view-функция получает данные, кладёт их в контекст и вызывает
`render()`. Функция `page()` из ПР5 больше не используется и удалена.

### Базовый шаблон и наследование

Общая структура всех страниц находится в `templates/base.html`: объявление
документа, кодировка, заголовок вкладки, Bootstrap, собственный CSS, логотип,
навигация, контейнер содержимого, подвал и подключение JavaScript. Дочерние
шаблоны подключают его через `{% extends "base.html" %}` и переопределяют
блоки `{% block title %}` и `{% block content %}`.

### Включаемые шаблоны

Повторяющиеся фрагменты вынесены в отдельные шаблоны и подключаются через
`{% include %}`:

* `templates/includes/navigation.html` — навигация (подключена в `base.html`);
* `exercises/includes/exercise_card.html` — карточка упражнения в списке;
* `workouts/includes/workout_status.html` — статус тренировки (активна или
  отменена) в списке и на странице тренировки.

### Контекст, циклы и условия

View-функции передают данные словарём контекста, например
`{"exercises": exercises_list}`, а шаблон обращается к ним по имени:
`{% for exercise in exercises %}`. Для пустых коллекций используется
`{% empty %}`, для разных состояний данных — `{% if %}` (отменённая и активная
тренировка, наличие или отсутствие объекта на странице детали).

### Именованные URL и пространства имён

В `urls.py` каждого приложения задан `app_name` и имена маршрутов
(`homepage:index`, `exercises:list`, `exercises:detail`, `workouts:list`,
`workouts:detail`). Ссылки в шаблонах строятся тегом `{% url %}`, например
`{% url 'exercises:detail' exercise.id %}`, а не записываются адресом вручную.

### Фильтры шаблонов

* `{{ exercises|length }}` — количество элементов списка;
* `{{ exercise.name|default:"Без названия" }}` — значение по умолчанию;
* `{{ workout.workout_date|date:"d.m.Y" }}` — формат даты.

Фильтры отвечают только за представление данных, бизнес-логика остаётся в
Python-коде (`models/`).

### Статические файлы

Статика находится в `homepage/static/homepage/`: `css/style.css` (собственные
стили карточек, статуса и логотипа), `js/main.js` (подстановка текущего года в
подвал), `img/logo.png` (логотип). В шаблонах используются `{% load static %}`
и `{% static %}`. Bootstrap сохранён для базовой вёрстки, собственный CSS его
дополняет.

### Данные

С ПР9 view-функции получают данные через Django ORM (подробнее — в разделе
«Django ORM и модели (ПР9)»). В шаблон через контекст передаются объекты моделей
и наборы `QuerySet`, поля и связанные объекты доступны через точку:
`{{ workout.user.name }}`, `{{ item.exercise.name }}`. Ссылки пагинации строятся
тегом `{% querystring %}`, который сохраняет остальные параметры запроса.

## База данных SQLite (ПР7)

Файл базы данных ПР7 — `data/workout_app.sqlite` (отдельный от базы Django
`db.sqlite3`). В ПР7 работа с ним велась напрямую через `sqlite3` и
SQL-запросы. С ПР9 представления Django больше не обращаются к этому файлу:
он сохранён как исходная база, из которой данные переносятся в модели Django,
а SQL-слой (`sql/`, `db/database.py`, `db/import_json.py`) оставлен как
реализация ПР7 и используется скриптами переноса.

### Таблицы

**`users`** — пользователи

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор |
| `name` | TEXT, NOT NULL | имя |
| `registered_at` | TEXT, NOT NULL | дата регистрации, `YYYY-MM-DD` |

**`exercises`** — справочник упражнений

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор |
| `name` | TEXT, NOT NULL | название |
| `muscle_group` | TEXT, NOT NULL | группа мышц |

**`workouts`** — тренировки

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор |
| `user_id` | INTEGER, NOT NULL, FOREIGN KEY → `users.id` | пользователь |
| `workout_date` | TEXT, NOT NULL | дата, `YYYY-MM-DD` |
| `workout_type` | TEXT, NOT NULL, CHECK | «кардио» или «силовая» |
| `duration_min` | INTEGER, NOT NULL, DEFAULT 0 | длительность в минутах |
| `is_cancelled` | INTEGER, NOT NULL, DEFAULT 0 | 0 — активна, 1 — отменена |

**`workout_exercises`** — выполненные упражнения тренировки (связь «многие ко
многим» между `workouts` и `exercises`; в JSON это вложенный список
`exercises`)

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор |
| `workout_id` | INTEGER, NOT NULL, FOREIGN KEY → `workouts.id` | тренировка |
| `exercise_id` | INTEGER, NOT NULL, FOREIGN KEY → `exercises.id` | упражнение |
| `sets` | INTEGER, NOT NULL, CHECK >= 0 | подходы |
| `reps` | INTEGER, NOT NULL, CHECK >= 0 | повторения |
| `weight` | REAL, NOT NULL, DEFAULT 0 | вес, кг |

**`results`** — результаты за период

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор |
| `user_id` | INTEGER, NOT NULL, FOREIGN KEY → `users.id` | пользователь |
| `period_start`, `period_end` | TEXT, NOT NULL | границы периода (конец не раньше начала) |

**`result_workouts`** — тренировки, вошедшие в результат (в JSON — список
`workout_ids`). Составной первичный ключ (`result_id`, `workout_id`), оба
поля — внешние ключи на `results.id` и `workouts.id`.

Связи: у пользователя много тренировок и результатов; тренировка состоит из
нескольких выполненных упражнений; результат включает несколько тренировок.
Значения NULL в таблицах не допускаются: все поля обязательны (необязательное
в JSON `duration_min` при импорте получает значение по умолчанию 0).
Логическое значение `is_cancelled` хранится числом 0/1, даты — строками
`YYYY-MM-DD`, поэтому их можно сравнивать и сортировать средствами SQL.

* `data/workout_app.sqlite` — файл базы данных.

### Создание базы и перенос данных

Из корня проекта:

```text
python -m db.import_json
```

Команда создаёт файл базы и таблицы (если их ещё нет), очищает таблицы и
переносит данные из JSON через `executemany()` в одной транзакции
(`commit()` при успехе, `rollback()` при ошибке). Порядок импорта важен:
сначала `users` и `exercises`, затем `workouts` и `workout_exercises`, затем
`results` и `result_workouts` — иначе внешние ключи ссылались бы на ещё не
существующие записи. Повторный запуск возвращает базу к состоянию JSON.

Отдельно схему можно применить так:

```text
python -c "import sqlite3; c=sqlite3.connect('data/workout_app.sqlite'); c.executescript(open('sql/schema.sql', encoding='utf-8').read()); c.commit(); c.close()"
```

Проверка в SQLite CLI:

```text
sqlite3 data/workout_app.sqlite
sqlite> .tables
sqlite> SELECT COUNT(*) FROM workouts;
```

Запросы из `sql/queries.sql` можно выполнить все сразу:
`sqlite3 -header -column data/workout_app.sqlite < sql/queries.sql`.
Демо-данные: `sqlite3 data/workout_app.sqlite < sql/demo_data.sql`
(один раз; вернуться к данным JSON — `python -m db.import_json`).

### Получение данных в Django-представлениях (ПР7, заменено в ПР9)

До ПР9 представления открывали соединение функцией `get_connection()`, задавали
`conn.row_factory = sqlite3.Row` (строки результата доступны по именам
столбцов: `row["name"]` в Python и `{{ row.name }}` в шаблоне, без привязки
к порядку столбцов в запросе), выполняли запрос, получали `fetchall()` или
`fetchone()` и закрывали соединение. Значения из URL и форм передавались только
параметрами (`?` и `:имя`), а не подстановкой в строку SQL: так пользовательский
ввод не может изменить текст запроса. Пустой результат запроса — не ошибка:
шаблон показывает сообщение через `{% empty %}`.

С ПР9 те же страницы (`/exercises/`, `/exercises/<id>/`, `/exercises/search/`,
`/workouts/`, `/workouts/<id>/`, `/workouts/statistics/`) получают данные через
ORM; прямых SQL-запросов в представлениях не осталось. SQL-запросы
`sql/queries.sql` сохранены как справочный материал ПР7 и для проверки в
SQLite CLI.

## Django ORM и модели (ПР9)

В ПР9 слой данных переведён с ручных SQL-запросов (`sqlite3`) на модели Django
и Django ORM. Предметная область, страницы и пользовательские сценарии
сохранены, изменился способ получения данных.

### Стратегия перехода

Выбран вариант «таблицы, управляемые Django, и перенос данных»: прежняя база
`data/workout_app.sqlite` не изменяется (скрипты открывают её только для
чтения), Django создаёт свои таблицы миграциями в `db.sqlite3`, после чего
данные переносятся через ORM с сохранением идентификаторов и связей. Настройка
`DATABASES` указывает на `db.sqlite3`.

### Модели и связи

| Приложение | Модель | Поля | Связи |
|---|---|---|---|
| `users` | `User` | `name`, `registered_at` | — |
| `exercises` | `Exercise` | `name`, `muscle_group` | — |
| `workouts` | `Workout` | `workout_date`, `workout_type` (выбор: кардио / силовая), `duration_min`, `is_cancelled` | `user` → `User` (`PROTECT`, `related_name="workouts"`); `exercises` → `Exercise` через `WorkoutExercise` (`related_name="workouts"`) |
| `workouts` | `WorkoutExercise` | `sets`, `reps`, `weight` | `workout` → `Workout` (`CASCADE`, `related_name="workout_exercises"`); `exercise` → `Exercise` (`PROTECT`, `related_name="workout_exercises"`) |
| `results` | `Result` | `period_start`, `period_end` | `user` → `User` (`PROTECT`, `related_name="results"`); `workouts` → `Workout` (`ManyToManyField`, `related_name="results"`) |

`User` — модель предметной области, а не встроенная модель аутентификации
Django. Первичные ключи (`id`) создаются Django автоматически.

Правила предметной области в моделях:

* подходы и повторения не меньше нуля — `PositiveIntegerField`, вес не меньше
  нуля — `CheckConstraint` и валидатор;
* конец периода результата не раньше начала — `CheckConstraint`;
* дата тренировки не в будущем — `Workout.clean()` (срабатывает при
  `full_clean()` и в админ-зоне);
* тип тренировки только «кардио» или «силовая» — `choices`;
* отмена тренировки — метод `Workout.cancel()` (запись остаётся в базе);
* пользователя с тренировками и упражнение, которое используется в
  тренировках, удалить нельзя (`PROTECT`), строки упражнений удаляются вместе
  с тренировкой (`CASCADE`);
* тренировка не создаётся без упражнений — `workouts.services.create_workout()`
  проверяет правила и сохраняет тренировку со строками одной транзакцией.

### Миграции и перенос данных

```text
python manage.py makemigrations     # файлы миграций уже есть в репозитории
python manage.py showmigrations
python manage.py migrate
python -m db.inspect_source_db      # осмотр базы ПР7 и проверка внешних ключей
python -m db.import_sqlite_to_orm   # перенос данных в модели Django
```

Файлы миграций (`*/migrations/0001_initial.py`) хранятся в Git. Скрипт
`db/inspect_source_db.py` показывает таблицы, столбцы, число записей и находит
внешние ключи, указывающие на несуществующие записи. Скрипт
`db/import_sqlite_to_orm.py` переносит данные в порядке зависимостей
(пользователи, упражнения, тренировки, строки упражнений, результаты и их
тренировки) одной транзакцией `transaction.atomic()`, преобразует даты в
`date`, сохраняет первичные ключи и безопасен при повторном запуске
(`update_or_create`). Если в исходной базе нарушена ссылочная целостность,
перенос не начинается.

### ORM-запросы проекта

Все запросы выполняются в представлениях и используются по назначению.

| № | Вид | Выражение | Где |
|---|---|---|---|
| 1 | набор объектов, сортировка по полю | `Exercise.objects.order_by("name")` | `exercises()` |
| 2 | один объект | `Exercise.objects.get(pk=...)` | `exercise_detail()` |
| 3 | один объект и связь | `Workout.objects.select_related("user").get(pk=...)` | `workout_detail()` |
| 4 | обратная связь, фильтр, `distinct` | `exercise.workouts.filter(is_cancelled=False).distinct().count()` | `exercise_detail()` |
| 5 | фильтр и `exclude()` | `Exercise.objects.filter(muscle_group=...).exclude(pk=...)` | `exercise_detail()` |
| 6 | фильтр по нескольким условиям, поиск по строке | `Exercise.objects.filter(muscle_group=..., name__icontains=...)` | `exercise_search()` |
| 7 | сокращённый набор полей | `Exercise.objects.values_list("muscle_group", flat=True).distinct()` | `exercise_search()` |
| 8 | `annotate`, `select_related` | `Workout.objects.select_related("user").annotate(Count(...), Sum(F * F * F))` | `workouts()` |
| 9 | поиск по нескольким полям, в том числе связанной модели | `filter(Q(user__name__icontains=q) \| Q(workout_type__icontains=q))` | `workouts()` |
| 10 | фильтры по нескольким условиям (признак, диапазон дат, тип, пользователь) | `filter(is_cancelled=False)`, `filter(workout_date__gte=...)`, `filter(user_id=...)` | `workouts()` |
| 11 | сортировка по нескольким полям и полю связанной модели | `order_by(*SORT_FIELDS[sort])` (`user__name`, `-workout_date`) | `workouts()` |
| 12 | постраничный вывод | `Paginator(queryset, PAGE_SIZE).get_page(page)` | `workouts()` |
| 13 | связанные объекты | `workout.workout_exercises.select_related("exercise")` | `workout_detail()` |
| 14 | `aggregate` | `aggregate(Count, Avg, Min, Max)` по активным тренировкам | `statistics()` |
| 15 | `annotate` с условным `Count` | `Exercise.objects.annotate(Count(..., filter=Q(...), distinct=True))` | `statistics()` |
| 16 | фильтр по связанной модели, `values` и `annotate` | `WorkoutExercise.objects.filter(workout__is_cancelled=False).values(...).annotate(Sum(...))` | `statistics()` |
| 17 | `annotate` и фильтр по агрегату (`HAVING`) | `User.objects.filter(...).annotate(Count, Sum).filter(workouts_count__gte=N)` | `statistics()` |

Особенности реализации:

* поле сортировки выбирается по словарю `SORT_FIELDS`, а не передаётся в
  `order_by()` из запроса;
* отменённые тренировки не входят в статистику; упражнения и тренировки без
  связанных записей остаются в списках (с нулями);
* `select_related()` загружает связанные объекты тем же запросом, поэтому
  список тренировок не делает по запросу на каждую строку (это проверяют
  тесты);
* значения из GET-параметров ORM подставляет параметрами запроса, поэтому
  ввод пользователя не может изменить текст SQL.

### Работа с объектами в Django shell

```text
python manage.py shell
>>> from users.models import User
>>> user = User.objects.create(name="Тест")          # создание
>>> user.name = "Тест 2"; user.save()                # изменение
>>> user.workouts.all()                              # обратная связь
>>> user.delete()                                    # удаление
```

Для просмотра и ручного добавления записей (например, чтобы увидеть
пагинацию, которая появляется при числе тренировок больше `PAGE_SIZE = 5`)
можно использовать админ-зону: `python manage.py createsuperuser`, затем
`http://127.0.0.1:8000/admin/` — модели зарегистрированы.

### Ограничения

* SQLite сравнивает регистр без учёта только у латинских букв, поэтому
  `icontains` для кириллицы регистр учитывает (так же вёл себя `LIKE` в ПР7);
* формы создания, изменения и удаления в веб-интерфейсе появятся в следующих
  работах; сейчас эти операции выполняются через ORM (shell, админ-зона,
  `create_workout()`).

верните `True` после проверки.

## Тестирование

```text
pytest -v
```

Тесты покрывают сущности предметной области (`test_exercises.py`,
`test_users.py`, `test_workouts.py`, `test_results.py`), загрузку и
сохранение JSON (`test_storage.py`) и веб-слой: страницы, коды ответов и
страницу 404, базовый шаблон, статику и именованные URL (`test_web.py`).
Слой SQLite ПР7 проверяет `test_db.py`: создание схемы, внешние ключи и
`CHECK`, импорт из JSON. Модели Django проверяет `test_models.py`: поля,
связи и обратные связи, `PROTECT` и `CASCADE`, ограничения базы, `cancel()`,
правила `create_workout()`, отсутствие неприменённых миграций. Перенос данных
проверяет `test_import_orm.py`: совпадение числа записей, сохранение ключей,
связей и дат, повторный запуск, неизменность исходной базы, остановку при
нарушении внешних ключей. Страницы с данными из ORM проверяет
`test_orm_queries.py`: фильтры, поиск, сортировку (в том числе недопустимые
значения), постраничный вывод и сохранение параметров в ссылках, отсутствие
запроса на каждую строку списка, статистику без отменённых тренировок, пустые
результаты и некорректные параметры. Тесты работают с отдельной тестовой
базой Django, рабочие файлы `db.sqlite3` и `data/workout_app.sqlite` не
изменяются.
